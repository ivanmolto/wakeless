# Program-owned escrow inside the PER

Task 2.5, open question 8 of the briefing. Read on 1 Nov 2026, no code written, nothing run on devnet. This document decides the v2 MagicBlock binding: whether an Anchor program delegated into a Private Ephemeral Rollup (PER) can hold the Wakeless escrow and release to a vendor against a voucher, instead of the v1 facilitator keypair.

The privacy claim is against the public ledger. Three operators see inside in v1: the facilitator (vouchers), MagicBlock's enclave (private transfers), NEAR's private shard (funding origin and route). A program-owned escrow removes the facilitator from the list of parties that can move funds; it does not remove the enclave.

The "PER permission example" the task names is `private-counter` (the repository's own label is "Anchor counter with permissions"); `sealed-auction` is the only example that combines a permissioned account with a program-owned token escrow, so it carries most of the weight below. The private-payments submodule was not initialised; the Private Payments API behaviour quoted here comes from the task 1.2 spike (briefing, open questions 1 to 4) and the public docs.

## 1. Can a delegated Anchor program hold an escrow balance and release to a third party on a condition, without the buyer signing at release time?

**Yes.** `sealed-auction` does exactly this.

- **Custody.** The auction PDA owns a Token-B ephemeral token account (eATA) under the Ephemeral SPL Token program `SPLxh1LVZzEkX99H6rqYizhytLWPZVV296zyYDPagv2`, created and delegated to the ER by the program itself through two raw CPIs (`init_ephemeral_ata`, `delegate_ephemeral_ata`, `sealed-auction/.../lib.rs:600-678`), with the validator pinned (`:109-119`). The docs' smart-contract-integration page states the rule the example follows: a plain PDA-owned ATA cannot be delegated; token custody on the ER goes through an eATA whose owner is the custody PDA.
- **Deposit.** Bidders move tokens into the escrow with an ordinary SPL `transfer` CPI on the ER, signed by the bidder (`place_bid`, `:198-208`). This is the one signature the payer gives, at deposit time. The Wakeless equivalent is the buyer's private deposit, which v1 already has.
- **Release without the payer.** `settle_winning_bid` pays the seller from the escrow with `CpiContext::new_with_signer` and the auction PDA's seeds (`:479-490`); its `crank` account is an `UncheckedAccount` with the comment "Anyone can crank this" (`:963-965`). `claim_refund` pays a bidder back with the same PDA signature, and the bidder is an `UncheckedAccount`, not a `Signer` (`:1013-1015`, `:547-558`). The condition is whatever the program checks: here the recorded `highest_bidder` and the `Bid` record (`:453-467`).
- **Simplest form.** `spl-tokens` is the same CPI with no custody: an `#[ephemeral]` Anchor program calling `token::transfer` on delegated token accounts on the ER (`spl-tokens/.../lib.rs:14-28`), confirmed by `tests/spl-tokens.ts:422-455`.

For Wakeless the condition at release is "a voucher signed by the buyer for a cumulative amount not yet redeemed, within the channel's deposit", and the submitter is the vendor or the facilitator acting as crank. Answer 4 covers whether the program can check that voucher.

Two conditions carry over from the spike: a recipient needs its own delegated eATA before it can receive (vendor onboarding is one base-layer transaction naming the vendor and the vault), and `split`, random delay and the 0.1% privacy fee are Private Payments API behaviours, not token-program behaviours; a program-driven transfer is one SPL instruction with no fee and no delay unless the program adds them.

## 2. What does the base layer see when such a program commits?

**The committed account's full bytes, in plaintext.** A commit is not a hash.

- The current delegation program (`DELeGGvXpWV2fqJUhqcF5ZSYMS4JTLjteaAMARRSaeSh`, fraud-proof design MIMD-0024) has the operator write the account's new data into a `StateBuffer` PDA in chunks (`write_state_buffer.rs:129-175`), post a `PendingCommitment` holding `data_hash`, `account_state_hash` and `state_commitment_hash` (`mimd-0024-fraud-proofs.md:147-171`, `:399-411`), and on `FinalizeCommitment` resize the delegated account and `copy_from_slice(raw_state)` into it after settling lamports (`finalize_commitment.rs:231-243`). The design notes say so directly: "the operator must write and finalize the DLP-owned `StateBuffer` before `ProposeCommitment`; the commitment stores hashes and the buffer stays available for finalization or dispute review" (`:56-61`).
- So every field of a committed account becomes readable on Solana: for an escrow program, channel records, cumulative amounts and vendor pubkeys, if they are in the committed account. The commit transactions are signed by the validator identity (`MTEWGuqxUpYZGFJQcp8tLN7x5v9BSeoFHYWQQ3n3xzo` on devnet), as the spike's validator-signed vault release was.
- Permission accounts are never committed: the docs state that `EphemeralPermission` accounts exist only on the ER, that there is no base-layer permission account to create, delegate or commit-and-undelegate, and that the data PDA pays their rent (also `private-counter/.../lib.rs:91-95`, `:219-221`). They do not protect a commit; they protect reads on the ER.
- Accounts created with `#[ephemeral_accounts]` / `eph` (the `Bid` PDAs, `sealed-auction/.../lib.rs:810-834`) live only on the ER and are closed there before the sponsor is undelegated (`undelegate_auction` requires `closed_bid_count == bid_count`, `:345-364`). They never reach the base layer.
- The spike confirms the token side: an ephemeral-to-ephemeral private transfer produced no base-layer signature and no commit; the base layer saw only the vault deposit and the vault withdrawal (briefing, open question 1).

**Consequence for the design.** The escrow program must never commit per-channel state. Channel records are `eph` accounts sponsored by the escrow PDA, closed on channel close; the escrow PDA itself holds only configuration (mint, authority, fee parameters) and may be committed; the escrow eATA is committed only on undelegation, when its single aggregate balance becomes public, which is the same exposure v1 has at vault withdrawal. `MagicIntentBundleBuilder::commit` is never called on a channel account. A test asserts the program's instruction surface has no commit path that names a channel record.

## 3. Who can read the program's state under the permission model?

**On the ER: the listed members of each account's permission, authenticated by an auth token; by default everyone. The enclave operator always. On the base layer: whatever was committed, everyone.**

- **Model.** One permission PDA per permissioned account, seeds `[PERMISSION_SEED, account]` under the Permission Program `ACLseoPoyC3cBqoUtkbjZ4aDrkurZW86v19pXz2XQnp1`, created, updated and closed on the ER by PDA-signed CPIs (`CreateEphemeralPermissionCpi`, `UpdateEphemeralPermissionCpi`, `CloseEphemeralPermissionCpi`; `private-counter/.../lib.rs:96-177`). The permission holds `is_private` and a member list, each member a pubkey and a flags bitmask: `AUTHORITY_FLAG` (modify the permission, add or remove members), `TX_LOGS_FLAG` (transaction logs), `TX_MESSAGE_FLAG` (transaction message data), `TX_BALANCES_FLAG` (balance changes), and `ACCOUNT_SIGNATURES` (docs only; the examples use the first four, `sealed-auction/.../lib.rs:581-586`).
- **Default.** "Every account is public by default, like in Solana" (on-chain-privacy page). `is_private: false` with an empty member list is fully public (`private-counter/.../lib.rs:113-116`); `is_private: true` restricts reads to the members (`:134-141`). The docs recommend rebuilding the full member list on every update so the authority is never locked out, which `set_privacy` does.
- **Authentication.** A reader obtains a token from the TEE RPC by signing a challenge with the member key (`getAuthToken`, `private-counter/.../tests/private-counter.ts:72-88`; `sealed-auction/.../tests/sealed-auction.ts:336-351`) and appends it to the RPC URL. Locally the Query Filtering Service "replicates the privacy logic happening on TEE nodes" (examples README; `scripts/local-env.sh:12`). The enforcement code is not in the open `magicblock-validator` or `magicblock-engine` repositories at the revisions read (no `is_private`, flag or Permission Program reference in either), so the read filter is part of the TEE RPC front, not auditable from source here.
- **What a non-member sees.** The spike measured it: `getTransaction` on the TEE RPC returned an ephemeral transaction with `err: null` and no account keys, logs or token balances, identically for sender, recipient and a third party (briefing, open question 2). The docs do not describe the non-member response; the spike's reading is the one the README quotes.
- **Granularity.** Permission is per account, read-side only. The docs say a permission today "grants read access to a delegated account" and that read/write splits may come later. The program itself reads and writes any account during execution; permissions do not gate instructions. The example that matters: `sealed-auction` keeps the auction PDA public, because "it does not store bid amounts or bidder keys" (README, flow step 3), and makes each `Bid` private with members auctioneer and bidder (`:255-271`).
- **The operator.** The TEE protects state from the host; the enclave executes every instruction in plaintext. MagicBlock's enclave stays on the list of operators who see inside.

**Consequence for the design.** The escrow PDA is public and holds nothing a watcher could use. Each channel record is private with members facilitator and buyer, never the vendor; each vendor's eATA is private with the vendor as member (the Private Payments API's `private: true` deposit does this for its own eATAs today). One gap: whether a program can create a permission for an eATA it owns, since `CreateEphemeralPermissionCpi` wants the permissioned account to sign (`permissioned_account` is the PDA signing with its seeds in every example) and an eATA is a PDA of the token program, not of the escrow program. No example does it. This is the first item for the v2 spike.

## 4. Could a signed voucher be checked inside the program without the amount leaving the enclave?

**In principle yes; unverified on the devnet TEE.**

- **Mechanism.** The standard Solana pattern: the transaction carries an `Ed25519SigVerify111111111111111111111111111` instruction over the voucher bytes, and the program introspects it through the instructions sysvar to bind signer, message and amount. The ER executes Agave 4.2.2's SVM: `magicblock-validator/Cargo.toml:94` pins `agave-precompiles = "=4.2.2"`, and the engine wires it into the runtime (`magicblock-engine/processor/src/callback.rs:46-61`, `is_precompile` / `process_precompile` delegating to `agave_precompiles`). So the Ed25519 precompile is present in the runtime that runs delegated programs. No example in the repository uses it, and no doc page lists supported precompiles or sysvars, so the claim is read from the runtime's dependencies, not from a run.
- **Where the amount lives.** The voucher (channel id, cumulative amount, signature) travels in the ER transaction's instruction data. That transaction is never broadcast to the base layer (answer 2; spike question 1), and its message data is readable on the ER only by members holding `TX_MESSAGE_FLAG` on the accounts it touches (answer 3). The amount therefore reaches: the enclave, the submitter, and the permission members. It reaches no base-layer observer as long as the channel record is never committed.
- **Commitment versus plaintext.** The briefing's v2 table puts a hash or Pedersen commitment to the cumulative amount in the voucher. Inside the PER a commitment buys nothing against the enclave, which must see the opening to check the balance, and nothing against the ledger, which sees neither. Its value is for the Rings binding, where a circuit checks the redemption and the prover is local, and for keeping one voucher format across bindings. For the MagicBlock binding alone, a plaintext Ed25519 voucher checked by the program is the simpler and equally private option; the `BatchVoucher` message of `docs/SCHEME.md` can be reused unchanged.
- **What the program checks.** Signature by the channel's `payerAuthorizer` (the Ed25519 instruction), `channelId` match, `cumulative > redeemed`, `cumulative <= deposit`, then `transfer(cumulative - redeemed)` from the escrow eATA to the vendor eATA with the escrow PDA's seeds, and `redeemed = cumulative`. This is the public payment-channels program's `settle` logic with the ledger exposure removed. The buyer's loss stays bounded by what it signed; the facilitator can no longer misroute.
- **Open items for the spike.** (a) An Ed25519 instruction plus sysvar introspection on `https://devnet-tee.magicblock.app`, in a transaction that touches a private account. (b) Whether the instructions sysvar is populated in the ER. (c) Compute cost of the introspection inside the runtime limits. None of these is a design question; each is one devnet transaction.

## Conclusion

The examples show a delegated program holding an eATA escrow and paying a third party on a program-checked condition with a PDA signature, so the custody and release halves hold; commits are plaintext, so channel state must stay in ER-only accounts; reads are gated per account by permission members; and the runtime carries the Ed25519 precompile, so the voucher can be checked where the amount already is, with the eATA-permission and devnet-precompile checks left for the v2 spike.

Verdict: v2 program-owned escrow feasible as designed.
